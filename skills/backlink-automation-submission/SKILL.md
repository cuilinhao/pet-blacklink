## When to use

Use this skill when the user wants to submit backlinks / product listings / directory listings / technical audit pages for one or more websites, especially when using Hermes Agent with a real Chrome browser controlled by OpenCLI.

Also use it when the user explicitly selects a backlink-sample CSV such as `gefei0810.csv` whose rows contain `Type` and `URL` fields and must be processed in source order.

This skill is designed for white-hat, low-volume, manual-review-friendly backlink work. It is not for spam, mass posting, cloaking, fake accounts, comment spam, or bypassing anti-abuse systems.

## Core principle

The goal is not to click as many buttons as possible.

The goal is to create a reliable daily backlink SOP:

1. Read website profile.
2. Before opening any submission platform, audit the previous run's persisted cursor, reconcile it with historical records, and resume the target website's current platform CSV from the next truly unprocessed relevant row.
3. Submit or generate public pages carefully.
4. Take over the real computer when login, registration, email verification, or a one-time code interrupts the flow. Route CAPTCHA or human verification immediately through **CAPTCHA and human verification — automatic CapSolver routing**. Complete authorized steps autonomously whenever the active control tool permits it; pause only for a genuinely unavailable prerequisite or a tool/system-required confirmation or user-only handoff.
5. Verify evidence before counting.
6. Record every success, block, and failure.
7. Improve the platform notes after each run.
8. After persistence and verification, close the run's browser tabs so backlink work does not accumulate in Chrome.

### Mandatory product-truth gate for public content

Before drafting or publishing any article, profile, listing description, resource page, or other public content for a target website:

1. Read the target website profile and inspect at least one current first-party source of truth: the live official site, its current repository/README, or approved product documentation. Do this again when the product may have changed since an earlier run.
2. Write down the product's actual audience, core job, current features, and explicit limitations before composing. Resolve conflicts in favor of the most current first-party implementation or documentation; do not infer the product from its name, domain, category, or an older backlink draft.
3. Every concrete feature or workflow claim in the public content must be supported by those current first-party sources. Omit retired, planned, ambiguous, or unverified features and do not invent adjacent capabilities merely to make an article fit a platform.
4. Make the article's central topic directly match the product's real use case. A natural backlink inside otherwise unrelated content is not sufficient.
5. Before publication, compare the title, opening paragraph, product description, and link context against the verified product facts. If any of them describes a different product, rewrite before submitting and do not count the page until the corrected public version is verified.

Treat the user's instruction to use this skill for backlink submissions as standing pre-approval to upload any submission asset that is clearly associated with the target website and available in its profile or site-specific workspace assets. ### Executable resume gate

Do not rely on a prose-only review for the mandatory run-start gate. Run the bundled deterministic audit before opening any candidate platform:

On the fixed macOS workspace, run the gate with Homebrew Ruby because the gate requires the `public_suffix` gem for registrable-domain normalization. Do not use the system `/usr/bin/ruby`.

```bash
/opt/homebrew/opt/ruby/bin/ruby skills/backlink-automation-submission/scripts/resume_gate.rb \
  --workspace /absolute/path/to/backlink-workspace \
  --website "Target Website" \
  --active-csv "active-file.csv" \
  --today YYYY-MM-DD \
  --expect-next-source-key "active-file.csv::Platform::normalized-platform-identity"
```

Proceed only when the command exits `0`, prints `RESUME_GATE=PASS`, and reports the exact expected next source key. A nonzero exit, duplicate source key, same-day counted duplicate, or cursor mismatch is a hard stop: repair the records and rerun the gate before any browser interaction.

The script is a minimum mechanical guard, not a substitute for relevance, blacklist, payment, or safety review. In standard platform mode it treats a normalized platform domain as the same platform even when the CSV name, subdomain, `www` prefix, report ID, query string, or evidence URL changes. For shared hosts such as `tally.so`, `docs.google.com`, and `github.com`, it includes the hosted path in the identity. In backlink-sample mode it uses the normalized target page, including meaningful query parameters, as the cursor and duplicate identity.

Run this gate again after every persisted candidate outcome. The newly reported `next_source_key` becomes the only allowed next platform. Never jump to a later row from memory.

- Upsert that candidate's state, status, evidence, and notes in `records/platform-progress.csv`. Upsert means update the existing row in place when `(website, source_key)` already exists; never append a second row with the same key.
- Update today's active CSV, processed/remaining totals, and next cursor in `records/daily/YYYY-MM-DD.md`.
- Never keep a batch of inspected, submitted, paid, terminal, or deferred rows only in memory for later writing.
- After an interruption or hard stop, repeat the run-start resume gate and resume from the persisted first unprocessed row. Inspect any preserved draft before acting, and never submit it again when historical evidence already proves submission.
